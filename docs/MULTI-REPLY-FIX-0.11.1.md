# DSH 多段回答丢失修复（0.11.1）

## 复现与原因

通过实际 DshClient 订阅本机模拟 DSH 事件，再经过 Bridge、Media 和模拟 QQ 发送回执，复现了“同一回合工具调用前后产生三段正式回答，QQ 只收到最后一段”。旧版连续两次测试失败，实际投递仅最后一段。

原因是 DshClient 用单一 `turn.text` 覆盖每次 `assistant/message`，并只返回最后文本。该实现把插话时排除旧回答的需求扩大到了普通多段回答。Bridge 的宿主工具续答循环也只保留最后轮的解析结果。

## 修复行为

- QQ 路径请求完整消息集合，按事件顺序保留文字消息。每条消息仍独立解析 reply/memory/qq，不能简单拼接原始 JSON。
- 只有实际关联到本次请求的新 user/message（包括 steer）才推进回答代次；被插话替代的旧代次不投递，插话后多段新回答全部保留。
- 按事件序号去重，并按 assistant message ID 更新同一消息的最终版本。不同 ID 的相同文字不会被误删。快照、流式 chunk、思考块和工具输出不成为 QQ 回复。
- 保留宿主工具执行前后的 reply；内部 actions、memory、learning 由宿主处理，不原样发送 QQ。后台记忆整理继续取最终单一结构化结果，不把多段 JSON 拼接给解析器。
- 在 DSH 回合正常完成后统一准备和投递，并非即时转发流式输出。错误、取消、超时不会发出未完成回合的部分内容。
- 私聊按顺序发送；兼容的群聊文字/图片消息合并成一条、段落间留空行，避免同一轮的后续段落被最短发送间隔挡住。其他媒体仍遵守群发送限额；部分已发送后遭限额会记录错误，不自动重发。
- 长文本分段保留完整正文，避免旧版截取前 4000 字导致末尾丢失。每次 QQ 投递记录段号和总段数；第二段失败时保留第一段回执、停止后续发送，结果不确定时不补发。

## 测试边界

回归覆盖原始三段复现的私聊及群聊、跨 turn/end 的插话竞态、插话后多段回答、重复事件/消息更新、工具续答、内部内容过滤、无效 JSON、中途停止、部分发送失败、长正文与 emoji 边界。

使用本机模拟接口与临时记忆目录；没有真实 QQ 发消息或真实模型调用。没有批量补发过去丢失的历史回复，也未修改原插件源码或原 memory 核心。
