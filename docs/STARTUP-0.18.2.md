# 0.18.2 启动整理与上线招呼

## 0.18.6 行为更新

0.18.6：启动时按本地消息序号划定历史边界，旧未读与旧待处理记录只整理记忆、不补入回复队列；整理期间的新消息继续排队。引用查询失败保留原始记录，按引用不可读取继续参与判断，不阻塞后续消息。

历史边界在启动接收时同步保存，使用各聊天独立的本地序号，避免毫秒相同或客户端时间不准导致误分类。历史消息不标记为本轮待回复，也不自动拼进新消息上下文；原始记录、未读标记及记忆整理来源保留。旧队列仅改为 history 状态，未知执行结果仍保留原有防重放保护。

模型每轮收到回复范围规则与启动边界，只回应启动后收到的新消息；用户明确追问历史时可以参考记忆。失效引用无法确认来自机器人时按普通群聊参与规则处理，已有机器人发送回执可保留直接回复属性；不会绕过普通群聊冷却或 @ 权限。引用原文、编号保留，不再循环查询缺失引用。

以下为早期版本契约，旧未读回放回复行为已由本节替代。


启动某种聊天接收后，对该类型允许名单内的每个聊天独立执行：收集本地未读与未整理记录 → DSH 整理并取得记忆保存回执 → DSH 按本聊天 SOUL 人设生成一句上线招呼 → 通过统一 QQ 出口取得发送回执 → 处理排队消息。重复点击已经启动的类型不会重复招呼。

## 数据与顺序

- 聊天键仍为机器人账号 / private 或 group / 对象号码。不同群、不同私聊以及同号码的群和私聊拥有独立启动任务；一个聊天的整理不会阻塞另一个聊天。
- 资料来自本地消息索引、原始输入/快照、已完成对话和会话压缩；包含已读但尚未整理的原始记录、当前及保留会话的未整理记录。以实际保存回执判定整理覆盖，不用“已读”代替“已整理”。本功能不向 QQ 客户端补拉离线期间从未被服务接收的历史。
- 整理本身不消费 inbox、不清空待回复队列。整理和生成/发送招呼期间的新消息落盘等待。启动资料采用固定快照；之后新到的消息留给排队处理及后续记忆整理，避免群消息不断到来导致无法上线。
- 较多资料按不超过约 180000 字符的批次提交，逐批记录回执；单条过大时暂停并保留原文，不截断后冒充全部整理成功。失败重启时只重新整理缺少回执的资料。
- 启动后的积压消息在同聊天内逐项等待完成。普通群聊冷却只延迟普通群消息；@ 和确认引用机器人的消息可越过冷却中的普通消息，但不会并行启动同聊天模型回合。跳过的普通消息仍保留，也不会被顺带作为上下文消费。
- 既有持续对话的窗口内消息接收机制保持；原生执行仍按聊天隔离。后台空闲整理也改为每聊天独立调度。

## 失败和停止

- 未取得整理回执、关闭该聊天记忆、生成的招呼格式不合格或发送未成功时，该聊天暂停启动，保留待处理数据，不放行正常回复。面板显示阶段、批次进度、排队数和错误。
- 招呼只生成一句最多 200 字的自然文本，以本聊天的人设表达“我来了、现在在线”；不开放 QQ 工具给招呼生成回合。明确的后台输出通过统一发送出口投递，普通聊天正文仍不自动转发。既有允许名单、发送额度与最短发送间隔继续有效。
- 发送状态和启动阶段在投递前后持久化。发送结果未知或重启时仍处于投递阶段，停止自动重发，避免重复招呼；需人工核实。整理/消息执行未知结果也不会静默循环重试。
- 管理者明确停止依然可以取消；再次启动必须等旧任务退出。不会自动重新执行历史未读中的 `/stop` 等管理命令，也不会重新提交已有发送/未知发送记录的请求。
- 默认仍是停止接收；更新只替换服务和配套插件，保留配置、记忆、工作区和旧会话，不自动向真实聊天发测试消息。

## 验证入口

`standalone/test/startup-chat.test.mjs` 使用隔离临时记忆库、模拟 DSH 和模拟 OneBot，覆盖启动门禁、按人设生成、回执顺序、跨聊天独立、串行队列、@ 冷却旁路、批次恢复、未知投递、取消及真实 Bridge.start 接线。与已有 maintenance-inbox、lifecycle、service、channels 回归共同验证。实际模型的人设表现及真实 QQ 投递另行验收。
